K Goals-First IA Recommendation · Kustomer Platform
Analysis Prepared by Yvonne Doll, May 21 2026

A goals-first IA for the whole Kustomer platform.

Goals and Performance become core platform destinations alongside Inbox. Lower-frequency items move to overflow navigation, while the AI workspace focuses on one job: simplifying AIC and AIR configuration around organizational goals.

01Principles for the goals-first IA

  1. Goals are platform primitives. They live in the site rail. Every other destination references them.
  2. Outcome on Goals, operational on AI. Each goal shows its trajectory. AI → Analyze shows whether the automation is healthy. Performance is the cross-goal operational rollup.
  3. Setup, not configuration. AIC and AIR each get one opinionated setup surface. Defaults loud, advanced knobs quiet.
  4. One wizard, two branches. Get Started asks AIC, AIR, or both, then runs the right sequence end to end.
  5. Goal context follows the user. Conversations, alerts, suggestions, and report rows know which goals they touch and link back.
  6. Automations are first-class and shared. Procedures, tools, knowledge, and shared guardrails in Building Blocks are reused across automations. Edits propagate.
  7. Per-automation settings live with the automation. Competitors, Secrets, Tone, greetings, verification, routing live on each automation's Settings. Shared guardrails (refund ceilings, escalation triggers) live in Building Blocks and attach inline.
  8. Topics are org-level. One canonical taxonomy under Reporting → Topics, auto-detected from history. Goals select a subset; everything else references the same list.
  9. Goals facet by audience, not by surface. Every goal carries an audience tag (AIC, AIR, Sales, Human Reps, Other). The Goals destination filters by audience; AI Setup pre-filters to AI goals.
  10. Advanced is preserved, not promoted. Build, Test, Deploy, Manage Automations get a LEGACY pill under a "For power users" subheader.
  11. Recommendations apply in place. Every suggestion carries an "Apply in [block]" CTA that opens the affected procedure / KB / tool / guardrail inline. No page jumping.
  12. Inline capture, canonical home, persistent provenance. Capture new data where it's first needed (Company profile, Topics, audience tags). Store at its canonical org-level home. Stamp the home on every consuming surface with an edit link.
  13. One lifecycle vocabulary: Build / Test / Deploy / Analyze. Same verbs in AI Setup, per-automation tabs, suggestion CTAs.
  14. One Build tab. First-run is a mode of it, not a separate destination. Creating a new automation routes the admin to the same per-automation Build tab they'd edit on day 90, with a stepper, locked future tabs, and parser-drafted callouts overlaid until Deploy activates. No parallel "wizard" surface.
  15. Build and Test share a right rail: Assistant + Test Console. Persistent, collapsible. Assistant chats about the open guidance; Test Console sends live messages on a chosen channel and brand. Same rail, same widget contract on both tabs.
  16. Procedures have associations, not owners. Every procedure declares which surfaces it applies to: scope labels ("All AI for Customers", "All AI for Reps") and specific automation ids. The library is the canonical home; each automation's Build shows its slice. Editing a multi-scope procedure fires a blast-radius prompt.
  17. Deploy is cross-audience by design. One page with audience banners: an AIC section (conditions, smart routing, eval recap) and an AIR section (Copilot toggle, mode, teams). Same Activate button covers both. AIR Settings still owns steady-state Copilot config; Deploy owns the activation moment.
  18. The recommendation→action loop is structural, not a link. Every suggestion names its target block. The loop has its own affordance, its own pattern.
  19. Three metric layers, one question each. Goals = "did we hit the outcome?" · Performance = "are agents healthy right now?" · Analyze = "is this automation behaving?" Each surface declares its layer in chrome; drill direction is one-way.

04The recommendation→action loop

The structural pattern that closes the gap between detection and fix. Every AI suggestion carries an explicit Apply in [block] affordance that opens the exact procedure, monitor, KB article, tool, guardrail, or coaching path being recommended, pre-scoped and ready to edit. The loop has its own affordance, its own pattern, its own home in the IA. It is the differentiator, not a footer link.

The six target blocks a suggestion can open
Apply in Procedure
Opens the procedure body with AI changes inline; lives in Building Blocks, attached to the automation.
Apply in Monitor

Apply in KB Article
Opens the Knowledge Source article with AI-drafted content additions or corrections.
Apply in Tool
Opens the tool config (auth, scope, parameters) with the proposed change pre-set.
Apply in Guardrail
Opens the per-automation guardrail or the shared guardrail rule with the new constraint pre-filled.
Apply in Coaching Path
For human-rep degradation: opens the coaching path with the targeted skill or scenario pre-selected.

05Risks the new Goals primitive introduces

The strategic costs of treating Goals and Topics as platform primitives and splitting outcome performance from operational performance. Severity reflects blast radius across personas.

# Risk Severity Why it hurts
1 Rail real estate High Goals and Performance newly promoted alongside the existing rail (Inbox, Searches, Reporting, TeamPulse, Rep Dashboard). Rail runs eight items deep before utility; Apps, KB, Widgets, Settings, Help all get pushed into overflow.
2 Cross-team primitive ownership High One Goal object. One edit surface. One set of display primitives with contextual variants — every surface picks a variant, no surface draws its own.
3 Audience + topic tag drift Medium Mis-tagged goals or conversations shatter every picker and rollup. Required-on-create, auto-detect confidence flags, and audit jobs mitigate.
4 Audience boundary ambiguity Medium "Improve CSAT" belongs to AIC, AIR, and Human Reps at once. Multi-select audience + primary-owner field + documented rubric.
5 Goal reports left Reporting Medium Goal-specific reports moved to Goals Home. Reporting users may not find them. Cross-link callouts from Data Explorer and Standard Reports.
6 Goal-attribution noise Medium Every block, toggle, monitor, and suggestion carries "drives Goal X" annotations. Without density rules they become wallpaper. Show only when scope is implied; cap per surface.
7 Primer skip + migration mis-mapping Low Admins skim primers. Mitigation: Company profile is captured inline during first goal creation (can't be skipped); make the primer re-openable from the avatar menu; the auto-lift of per-automation goals into platform Goals runs a one-time audit on migrated goals.
8 "Override" exit on Analyze Low The third branch (Override) ships an automation with a known-failing category. Goal page must flag it loudly so it isn't forgotten.
9 "Resources" renamed to Building Blocks Low Existing admins navigate by muscle memory. Add an inline "formerly Resources" hint for one release; redirect deep links.
10 Per-automation surface scope creep Low The per-automation Settings page could grow back into a multi-tab spread. New toggles default to advanced until usage promotes them.

06Friction points and resolutions

Each remaining tension in the proposed IA, paired with the standing contract that resolves it. Every contract below is documented in the relevant IA node so the resolution rides with the structure.

Friction What's happening Contract (documented in IA)
Goal authoring entry points diverge "+ Create goal" surfaces in six places: Goals Home, the Attached Goals card on Build, per-automation Settings, Manage Automations, AI Setup, and every goal-picker footer. One authoring component, the Create Goals slide-out. Every entry point opens it with audience + topics pre-filled and returns the saved goal pre-selected.
Outcome rollup vs operational rollup look alike Goals Home opens with an outcome summary ("hitting what we said?"). Performance is the operational rollup ("how are agents doing?"). Both look like dashboards. Distinct framing copy in each header; never duplicate tiles. Goals Home tiles deep-link to Performance; Performance rows link back to the goal.
Same primitives at platform and per-automation Monitors, Suggestions, Anomalies live as Performance children and as Analyze tabs inside every AIC automation. Same primitives, two scopes, unclear which to act on. Per-automation tabs own authoring (apply, dismiss). Performance is the aggregate. Rollup rows carry a scoping pill that deep-links to the source; sources footer-link to "across all automations".
Anomalies is AI-only inside a cross-agent rollup Performance's three children look like peers, but Anomalies (Validation Agent) is AI-only; only Monitors and Suggestions cover human work. "AI only" subhead on Anomalies + one-line explainer on Performance. Human degradation surfaces via Monitors (dips) and Suggestions (coaching).
Guardrails split into two flavors, one word Per-automation guardrails (Competitors, Secrets, Tone) live on each automation's Settings. Shared guardrails (refund ceilings, escalation triggers) live in Building Blocks. Same label, two homes. Rename in chrome: "Per-automation guardrails" on Settings, "Shared guardrails" in Building Blocks. Inline "+ Attach shared guardrail" on each automation's Settings.
"Mine" vs audience facets on Goals "Mine" overlaps with audience facets, an AI admin's "Mine" is almost always their AI goals. Pre-select the audience facet by viewer role; "Mine" filters within whatever facet is active.
Topics management vs Topics analytics Authoring (rename, merge, hide, custom instructions) lives in More → Settings → Topics. Analytics lives in Reporting → Topics. Same name, two homes. Keep each page single-purpose; both already cross-link. Never duplicate controls across them.
Computed Fields moved out of Building Blocks Computed Fields now live in More → Settings. AI admins who used to find them in the AI workspace may not discover the new home, and every goal threshold reads one. Cross-link every goal threshold and scorecard into Settings → Computed Fields, field pre-selected. Reverse-link each field to the goals and monitors it feeds.
AI Setup wizard duplicated per-automation tabs Old IA had AI Setup as a parallel surface authoring the same data the per-automation Build / Test / Deploy / Analyze tabs already capture, with the same verbs since the lifecycle-vocabulary rollout. Resolved. AI Setup is removed. "+ New automation" creates a row in Automations and routes to its Build tab in first-time mode (stepper, locked future tabs, parser callouts). Same URL, same surface, one place to author and edit.
AIC selector vs Manage Automations Clicking AI for Customers opens a switcher dropdown; Manage Automations is a separate destination. Both show the AIC automation list. Dropdown is switch-only: name + status pill + "→ Manage all" footer. Manage Automations owns add, edit, delete, duplicate, filter, sort, bulk.
Tools not visible in primary nav Shared Tools are the AI's hands, nesting them inside Building Blocks understates their operational weight when an integration breaks. Flyout on the Building Blocks rail row exposes Procedures, Knowledge Sources, Tools as one-click destinations.

Goals

Goals as a platform primitive. Authoring, scoping, leadership rollup, and goal-context-follows-the-user.

Monitors

Quality + Anomaly monitoring of live AI. Per-criterion drill-down, alerting, suggestions, runtime QA.

AI Config Setup

Goals-first intake, plan trust, staged testing, scoped deploy, closed-loop recommendations.

Goals

Maps to monitoring JTBD 1, 4, 8 + the leadership rollup pattern 5 tasks
1

Declare a new business goal from scratch

"You've been asked to reduce refund-related escalations. Set up a goal to track this."
Success
Participant lands on Goals, chooses Create, sets a target value, direction (lower is better), and unit without backtracking.
Tests
Goals as primitive, slide-out authoring, defaults vs. custom.
2

Scope a goal to a specific AI agent

"Your refund agent is one of three AI agents. You only want this goal to track that agent's performance."
Success
Participant finds the Goal Resource control and selects the correct AIC automation.
Tests
Resource scoping, goal-to-automation linkage, whether the relationship is discoverable.
3

Read the leadership rollup, identify an at-risk goal

"You're prepping for a Monday exec review. Tell me which goals are on track and which need attention."
Success
Participant uses Goals Home (cross-goal sparkline grid) to identify the at-risk goal within 30 seconds and can articulate why.
Tests
Outcome rollup legibility, at-risk lane, sparkline comprehension.
4

Trace a goal back to the conversations driving its score

"Your CSAT goal is dipping. Show me the conversations contributing to last week's drop."
Success
Participant drills from the goal into the linked monitor's flagged conversations.
Tests
Goal → Monitor → Conversation traceability, the "goal context follows the user" principle.
5

Edit a goal's target mid-flight

"Leadership has raised the bar, the team now needs to hit 90% CSAT instead of 85%. Update the goal."
Success
Participant finds the goal, opens it, edits the target, and saves without confusion about whether monitors or alerts need to be reconfigured.
Tests
Edit affordance, whether dependencies are surfaced, optimistic vs. anxious editing behavior.

Monitors

Maps to monitoring JTBD 2, 3, 5, 6, 7, 9 5 tasks
1

Find out why a specific conversation was flagged

"This conversation was flagged by your Quality Monitor. Tell me which criterion it failed and why."
Success
Participant opens the conversation, sees per-criterion scores, weights, pass/fail, and rationale.
Tests
Per-criterion drill-down (JTBD 5), readability of the rubric in context.
2

Configure a custom monitor with weighted criteria

"You want to start scoring AI conversations on tone and accuracy. Tone is twice as important as accuracy. If accuracy fails, the whole conversation fails."
Success
Participant creates a custom monitor, adds two criteria, sets weights, marks accuracy as essential, sets a pass threshold.
Tests
Criteria authoring (JTBD 9), the essential flag concept, weight comprehension.
3

Opt into alerting for a degrading monitor

"You want to be told within the hour if this monitor's pass rate drops. Set that up."
Success
Participant turns on alerts, selects hourly cadence, confirms delivery channel.
Tests
Opt-in alerting (JTBD 3), cadence selection, delivery channel clarity.
4

Act on an AI-generated suggestion from a failed monitor

"The monitor has produced a suggestion to update this procedure. Review it and either apply or dismiss it."
Success
Participant finds the suggestion card on the Suggestions & Alerts surface, reads confidence + goal tag + the before / after diff inline, clicks Edit Procedure to open the inline slide-out with the affected procedure and AI-marked changes, applies (or edits then saves) or dismisses with a reason. No page navigation.
Tests
Suggestion legibility (JTBD 6), before/after pattern, the inline slide-out edit-in-place affordance, dismiss-with-reason.
5

Review anomalies surfaced by the Validation Agent

"Your AI agent went off-script three times last week. Find those events and tell me what happened."
Success
Participant locates the Anomaly Detection Report, identifies the three events, and reads the anomaly type and affected resource.
Tests
Anomaly Detection discoverability (JTBD 7), the connection between anomalies and suggestions, runtime QA as a separate concept from post-call QA.

AI Config Setup

Maps to the four JTBDs in the Goals-Based AI Setup doc + the 5-page flow 5 tasks
1

Set up Kustomer AI for the first time, anchored on an outcome

"You just signed with Kustomer. You're responsible for reducing escalations on refund conversations. Get your AI configured."
Success
Participant completes the intake (company context, audience, goals, topics, monitors, knowledge, tone) without abandoning. Articulates that they're configuring around the escalation goal, not assembling parts.
Tests
The core thesis: goals-first intake feels different from configuration-first. Measure abandonment, backtracking, and post-task sentiment.
2

Review and trust the generated plan before saving

"Kustomer just generated a plan based on your answers. Walk me through what it's going to do, and tell me whether you'd save it as-is or change something."
Success
Participant can name what was generated (procedures, monitors, alerts, scope), identify which goal each item ties to, and edit at least one item.
Tests
Plan traceability (JTBD 2, "see what will change, where, and why"), blast-radius comprehension, editability of generated content.
3

Test the staged plan before deploying

"Before this goes live to customers, you want to make sure the AI handles refunds correctly. Test it."
Success
Participant finds the Test surface, runs an evaluation category against the staged plan, and interprets the readiness signal. Optionally uses the side panel test console for an ad-hoc conversation.
Tests
Discoverability of staged-vs-production distinction, readiness signal comprehension, the separation of save from activate.
4

Deploy with scope and capture a deploy note

"You're ready to turn this on, but only for chat conversations from your US brand. Deploy it."
Success
Participant scopes via rule groups (channel + brand), writes a deploy note, confirms.
Tests
Scope-then-activate pattern, rule group comprehension, whether the note feels valuable or like friction.
5

Act on a post-deploy recommendation, inline

"Two weeks in, your CSAT goal is drifting. Kustomer is recommending a procedure tweak. Apply it."
Success
Participant finds the suggestion where it lives in context (on the procedure card / in the suggestions queue), clicks View suggestion, the recommendation slides out with an inline edit view of the affected procedure, they apply or edit and confirm without leaving the current page.
Tests
The closed-loop story (JTBD 3, "tell me which lever to pull"), inline slide-out edit pattern (no page jump), preview-before-apply, version history awareness.
